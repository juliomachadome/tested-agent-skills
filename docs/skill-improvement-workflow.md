# Skill improvement workflow

Use this workflow with the [evaluation matrix](skill-evaluation-matrix.md). The matrix defines output quality and functional gates. This page proposes one change to investigate for each skill and gives maintainers a way to decide when the skill pays for itself. The proposals are hypotheses. Existing evidence remains in the [evaluation summary](evaluation-summary.md) and the [Codex evidence issue](https://github.com/juliomachadome/tested-agent-skills/issues/7).

## From a problem to a usage decision

1. **Choose a decision the skill should improve.** Start with a mistake someone has to correct or a task where the skill can offer useful judgment. Use a realistic brief that states the goal and actual constraints and leaves implementation choices open. Include a second case with different inputs and a near miss that should route elsewhere. Use a detailed brief as a separate case when the activation decision depends on how much guidance the user supplies.
2. **Fix the evaluation rule before generating.** Record the required behavior, quality criteria, minimum meaningful improvement, and any regression that blocks promotion. Choose evidence that fits the claim. Check arithmetic and execution with assertions, compare visual or written artifacts with the condition hidden, and observe people for usability claims. Keep held-out cases away from tuning and use synthetic inputs for public evidence.
3. **Run a cheap diagnostic pair.** Compare the current skill with a control without that skill. Keep the model, harness, effort, prompt, tools and inputs fixed within each pair. Use fresh sessions and verify the intended context. Record errors, ties, tokens, elapsed time, and avoidable rework. Start with one pair on a development case to decide whether more work is worthwhile. Use the matrix's repetition and review rules before making a quality claim.
4. **Change the smallest part that could explain the result.** Fix the description when the wrong tasks activate the skill. Fix the body when the right task receives bad guidance. Use a deterministic check when the requirement can be verified mechanically. Then compare control, current, and revised on the same cases. Document trade-offs by criterion and check the revision on a case reserved before editing.
5. **Check the supported harnesses, then record the decision.** For each case and harness, record the prompt ID, model, harness version, revision, how the skill was loaded, and evidence for the decision. State the next condition that would justify a retest. Publish aggregates and synthetic fixture identifiers. Keep private inputs, raw outputs, logs, and credentials out of the public repo.

| Outcome | Usage decision |
| --- | --- |
| The gain repeats on relevant tasks and required behavior is preserved | Recommend the skill for that task. Use activation checks before changing automatic routing. |
| The gain is specific to a task, brief, or harness | Recommend it conditionally and name that scope. |
| The outputs repeatedly tie and loading adds time or context | Leave it available on demand. |
| Loading repeatedly makes an important outcome worse | Avoid it for that task. Narrow the trigger or revise the guidance and retest. |
| Evidence is sparse, inconsistent, or missing for this harness | Record the outcome as inconclusive and keep the current routing while investigating. |

## Protect Claude Code while improving Codex

- For shared skill text, check installation and discovery through the existing paths on both [Codex](codex.md) and [Claude Code](claude-code.md). Use a matching brief and a near miss for trigger changes. A paired run that supplies the text explicitly answers whether the guidance helps. Test natural activation separately when the change affects how a skill is found or used.
- Compare current and revised within each harness using that harness's fixed model and configuration. Preserve required behavior and compare the declared quality criteria in Claude Code before recommending a shared revision. A missing Claude Code result leaves the shared change pending. If results diverge, retain the shared behavior and scope the guidance or activation to the harness where it helps.
- Evaluate `agent-orchestration` against a serial run in Claude Code. Evaluate `redigir` against unguided intake in Claude Code. Keep the [native agents and command conventions](compatibility.md) in their supported harness and test them there when a change touches them.
- Start with the cases that already have public fixtures and a clear failure or unresolved tie. Use `web-motion` for a mixed result and `qa-verification`, `customer-support`, and `software-security` to see whether quality review adds information beyond the gates. Next, favor repeatable fixtures for engineering and analysis. Schedule visual, usability and media cases when the people or artifacts needed to judge them are available. Stop an iteration when it has no specific decision or failure left to test.

## Proposals by skill

| Skill | Adjustment to test | Use or avoid hypothesis and decisive evidence |
| --- | --- | --- |
| `ad-creatives` | Put the product in action early and pair a concrete benefit with an approved claim. | Use for short ads built around a demonstration. Leave it off for spend diagnosis. Compare rendered openings for product recognition, visual clarity and reason to keep watching. |
| `agent-orchestration` | Delegate separable work and write down dependencies, ownership and where integration happens. | Use in Claude Code when independent work can finish concurrently. Use serial execution for a tightly coupled change. Compare completed scope, coordination mistakes, elapsed time and calls. |
| `business-model-finance` | Show contribution margin and cash timing separately, then vary the largest cost or loss assumption. | Use when a decision changes with volume, fees or cash timing. Use a calculation alone for a fixed one-line total. Check exact figures and whether the recommendation changes at the right threshold. |
| `cloud-deploy-ops` | Tie the health probe to the running revision and verify state after rollback. | Use for deployment incidents and recovery. Route in-browser jank to performance. Use a disposable service to measure correct diagnosis, restoration time and state after a retry. |
| `code-craft` | Freeze the first refactor, then reveal a second change to test the chosen design. | Use when a code path will evolve. Keep a mechanical edit small. Compare unchanged behavior, where the second change lands, duplicated decisions and extra abstractions. |
| `code-review-criteria` | Require a concrete failure and supporting diff evidence for each blocking finding. | Use for PR review. Route implementation requests to the relevant engineering skill. Measure seeded defects found, false positives on a clean PR and appropriate severity. |
| `copywriting` | Give each section a job. Remove repeated claims and test whether the opening makes the product and action clear. | Use when the message or hierarchy is unclear. Leave it off for a fixed correction with an approved voice. Compare comprehension, supported claims, voice and repeated information. |
| `customer-support` | Separate the policy decision from the reply and state the customer's immediate next action. | Use when a case may need escalation. Use the approved text for a routine acknowledgement. Compare matched tickets for correct disposition, clear next action and avoidable follow-up. |
| `data-analysis` | Reconcile populations, join cardinality, duplicates and missing values before comparing totals. | Use for a discrepancy or ambiguous population. Use direct arithmetic for known inputs. Verify exact totals, the diagnosed cause and a second data slice. |
| `data-engineering` | Declare how late, duplicate and corrected rows behave during loads and backfills. | Use for a repeatable data pipeline. Route a one-off reconciliation to analysis. Replay the same inputs and check final tables, recovery and unnecessary processing. |
| `data-visualization-dashboards` | Select the encoding after checking denominators, units, periods and uncertainty. | Use when the display should support a decision. Route unexplained source discrepancies to analysis first. Compare reader accuracy and time on a chart with unequal groups. |
| `engineering-playbook` | Verify how a change behaves on partial failure, retry and concurrent requests where relevant. | Use for changes touching persisted behavior. Keep simple presentation edits light. Check state and regression coverage after a failure and concurrent re-execution. |
| `growth-analytics` | Decompose a metric shift into instrumentation, traffic mix and within-segment behavior. | Use for unexplained funnel shifts. Route unrelated reconciliation to analysis. Measure whether the known cause is located and the next check separates competing explanations. |
| `lifecycle-messaging` | Model eligibility, repetition and exit before writing messages. | Use for event-driven sequences. Route a broken onboarding screen to UX. Replay repeated and out-of-order events and check recipients, timing and stopped sends. |
| `llm-engineering` | Score retrieval, source support and abstention separately. Track latency and tokens alongside quality. | Use when the system depends on model behavior. Use deterministic logic for a fixed transformation. Check supported answers and abstentions on unseen synthetic cases under a matched budget. |
| `market-research` | Rank evidence by commitment and state what observation would change the recommendation. | Use when demand is uncertain. Route established backlog priorities to product management. Compare how recommendations change when paid commitments conflict with attention or signup counts. |
| `media-production` | Inspect the actual render at the destination aspect ratio, with captions and audio enabled. | Use when a media file is the deliverable. Route a script-only request to the writing skill. Compare composition, continuity, audio, export constraints and production effort. |
| `mobile-app-engineering` | Make draft restoration and side effects explicit across suspended, resumed and terminated states. | Use for native lifecycle behavior. Route visual polish alone to UI. Reproduce lifecycle scenarios on iOS and Android and verify state, duplicate actions and responsiveness. |
| `offers` | Connect offer terms to actual objections and check margin under changed volume or costs. | Use when offer terms can change. Route rewriting approved terms to copywriting. Compare objection coverage and margin across scenarios. |
| `paid-traffic` | Separate noisy attribution from the suspected bottleneck and define a spending cap and stopping rule. | Use to diagnose acquisition. Route ad creation to the creative workflow. Check the known bottleneck, arithmetic, diagnostic value and budget in a synthetic account. |
| `process-improvement` | Measure active work, waiting, exceptions and rework independently before proposing automation. | Use for operational bottlenecks. Route product backlog choices to product management. Compare the recommendation on one viable automation and one case where the delay comes from a queue. |
| `product-creation` | Scope the first deliverable to a complete task that target users can try within the available capacity. | Use after credible demand evidence. Use market research when demand is unresolved. Compare a prototype's usefulness, scope and what a trial can establish. |
| `product-management` | Tie priority to evidence and dependencies, then recalculate the plan after a capacity change. | Use when work competes for a limited cycle. Keep a single settled task simple. Check that the revised plan preserves the goal and handles cuts and dependencies. |
| `qa-verification` | Link approval to the exact revision, built artifact and tests actually executed. | Use for release decisions with uncertain evidence. Keep a routine unit test review small. Verify that stale artifacts and skipped tests block approval while a clean control passes. |
| `redigir` | Reuse supplied facts and ask only for missing details that change the writing decision. | Use guided intake in Claude Code for incomplete briefs. Go straight to writing with an adequate brief. Compare questions, repeated answers and readiness of the resulting brief. |
| `sales` | Identify the known buyer objection and ask for a concrete, reversible next step. | Use for a stalled buying decision. Route a current customer's incident to support. Use a roleplay to compare diagnosis, next action and unsupported promises. |
| `seo-geo` | Examine canonical URLs, internal links and content intent on a crawlable fixture before recommending changes. | Use for discoverability work. Leave it off for writing with no search goal. Check whether the intended page is discoverable and answers the query. Ranking and citations require field evidence. |
| `software-architecture` | State the decisive constraint, recovery path and the change that would make a different design preferable. | Use for design decisions with system trade-offs. Route a local refactor to code craft. Verify the scenario constraints and compare adaptability when requirements change. |
| `software-security` | Turn the access policy into testable authorization cases, including revoked access and legitimate use. | Use when identity, role or workspace boundaries affect a decision. Leave it off for unrelated layout work. Check defensive policy outcomes across the permission matrix. |
| `storytelling` | Make the turning point follow from a choice and give it a visible consequence. | Use when adapting source material into a narrative. Leave it off for a straight factual summary. Ask readers to identify the turning point and verify facts against the source. |
| `ui-design` | Start with the content priority and inspect mobile, tablet and desktop at comparable states. | Use for visual hierarchy and responsive composition. Route broken journeys to UX. Compare typography, hierarchy, alignment and data legibility in a landing and a data-dense screen. |
| `ux-design` | Walk the first meaningful action and an error-recovery path using the same entry point and task. | Use when people cannot find, finish or recover from an action. Route typography-only changes to UI. Observe completion, hesitation, re-entry and keyboard recovery. Use unfamiliar-language navigation only for reversible tasks. |
| `viral-content` | Test who understands the premise and payoff in a rendered prototype. | Use for a piece intended to be shared organically. Route a defined paid campaign to ad creatives. Compare comprehension, attention and reasons to share. Measure reach separately after publication. |
| `web-motion` | Inspect the pivot, contact point and settled geometry of each moving part alongside its description and written fallback. | Use motion when the change teaches an action. Use a still when it already communicates the same thing. Judge labeled mobile frames, settled geometry, reduced motion and readability without JS. Test 3D viewers separately with load and idle rendering measurements. |
| `web-performance` | Reproduce and measure the bottleneck before changing the implementation. | Use for a demonstrated load, responsiveness or resource problem. Route motion design to web motion. Compare repeated runs on the same device profile and preserve behavior and data. |
