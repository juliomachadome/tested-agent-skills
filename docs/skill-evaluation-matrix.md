# Evaluation matrix by skill

This matrix proposes one starting case for each of the 35 catalog entries. It is a plan for future evaluations. These cases are not the historical holdout and the matrix contains no new scores or compatibility claims.

## How to use the matrix

1. **Brief the task.** Give the goal, source material and actual constraints. Include a complex task expressed in ordinary language. Leave out implementation decisions the skill should contribute. A fully specified brief can serve as a separate control.
2. **Separate the functional gate from quality.** Define both before generation. For a checkout, being able to retry is a gate; how quickly and confidently someone recovers is a UX question. For UI, use comparable screenshots and observable design criteria such as hierarchy, density and legibility.
3. **Run paired conditions.** Keep the model, harness, files, tools and limits fixed. Compare independent sessions with and without the target skill. Add a prior-version condition when evaluating a revision. Randomize order, hide labels from reviewers where practical, and report ties, losses and inconclusive runs.
4. **Collect evidence that fits the claim.** Inspect code and executed tests for engineering, artifacts for design, observed behavior for UX, and repeated measurements for performance. Report the dimensions separately. Calibrate reviewers with examples before scoring ambiguous criteria.
5. **Keep evaluation layers distinct.** Installation checks show availability; trigger and loading checks show whether the target skill was selected and read; paired quality checks show what the skill added to a specific task. Log the exact model, harness and version, skill revision, fixture identifier and hash, discovery mode, run count, outcome and limitations. Keep answers and logs private where required by the [security policy](../SECURITY.md).

For example, an inventory dashboard should fit narrow screens and preserve desktop comparison. To evaluate whether its layout serves the task, count **distinct urgent items visible**, regardless of whether they appear in a table, list or alert region. Compare screenshots at the same width and state. A count of table rows alone rewards one layout and can miss useful information elsewhere. The [public Codex pilots](https://github.com/juliomachadome/tested-agent-skills/issues/7) show both functional ties and differences in rendered output.

## Evidence and development status

Use deterministic checks for an objective gate, blinded artifact review for quality, and observation with people or field telemetry for claims about behavior. Record rubric points by dimension. For a new quality claim, start with two different cases and at least three independent pairs per case. Publish the rubric and a minimum meaningful difference before running. Call a win only when it reaches that difference without regressing a critical requirement. Show case-level results and distinguish ties from missing or inconclusive evidence.

Calibration and iteration use development cases. Lock a small, separate holdout before reviewing any revised output. Rotate exposed cases and version the fixtures. Track model calls, tokens, elapsed time, files observed, and dollar cost only where it is available. Evaluate native agents and command conventions in the appropriate harness, separately from skill quality.

## Engineering, quality and operations

| Skill | Short brief and fixture | Functional gate | What better looks like | Near miss and expected route |
| --- | --- | --- | --- | --- |
| `engineering-playbook` | “Retries create duplicate orders.” Give a small service with a known failure under retry. | Re-execution and concurrent requests leave the expected records. Regression tests pass. | Review the diff blind for clarity, fit with existing code, failure handling, necessary dependencies, and whether tests catch the original defect. | Choosing a service boundary or consistency model → software-architecture. |
| `code-craft` | “This pricing routine is hard to change.” Provide legacy code and a second rule change as a holdout. | Existing behavior passes characterization tests. | Measure effort to make the second change. Review coupling, readability, duplication and unused abstraction separately. | Filing findings on another person's diff → code-review-criteria. |
| `code-review-criteria` | “Can you review this PR?” Include known correctness defects and harmless changes, plus a clean PR. | Findings are grounded in the diff. The review accurately states what was run. | Measure defects found, false positives, severity calibration, and whether proposed fixes address the evidence. | Making a requested implementation change → engineering-playbook. |
| `qa-verification` | “Can this ship? CI is green.” Give a skipped test, stale artifact and a separate clean run. | No approval of a release with invalid evidence. | Measure detection of false greens and targeted risk coverage. Execute the proposed checks in the fixture and record their cost. | Confirming health and rollback on a live deployment → cloud-deploy-ops. |
| `software-architecture` | “Large exports freeze the app.” Supply workload and operational limits, then change one requirement. | Proposal meets integrity, workload and budget constraints in the fixture. | Compare the reasoning in the decision record, simplicity, failure recovery and the cost of adapting to the changed requirement. | Refactoring a routine inside a settled design → code-craft. |
| `software-security` | “How should access to private notes work?” Supply a synthetic role and workspace policy. | Authorization policy denies access when identity, membership or role cannot be verified. | Review defensive controls against the role matrix, including revocation and residual risk. Use policy assertions or static review. | Debugging an ordinary checkout layout → ux-design. |
| `data-engineering` | “The totals change when I reprocess the data.” Give late arrivals, duplicates and a backfill. | Output matches expected tables after a load, replay and backfill. | Measure idempotency, data contract checks, treatment of corrections, operator clarity and the cost of reprocessing. | Reconciling totals in a one-off extract → data-analysis. |
| `llm-engineering` | “My assistant cites the wrong document.” Provide a synthetic corpus and answerable and unanswerable questions. | Output matches the schema and citations refer to supplied material. | Score retrieval, citation support and abstention separately on held-out cases. Report tokens, latency and measured cost where available. | Asking for general warehouse ingestion → data-engineering. |
| `cloud-deploy-ops` | “The new build never gets healthy.” Use a disposable local service with a known failure. | Health check observes the intended build and rollback preserves fixture state. | Measure recovery time, diagnosis accuracy, rerun safety, log clarity and any remaining resource cost. | A local browser interaction janks with a healthy server → web-performance. |
| `mobile-app-engineering` | “The app loses my draft when I leave and come back.” Use a synthetic iOS and Android project. | The app builds and retains the draft across the specified transitions. | Verify lifecycle behavior on each named simulator or device. Measure responsiveness or resource use where relevant. | Reviewing the look of a native screen → ui-design. |
| `agent-orchestration` | “Organize these three workstreams.” Include independent work, a dependency and a review. | Dependencies and authorization boundaries hold. | Compare delivery quality, elapsed time, model calls and coordination errors with a serial run. Evaluate native delegation in the supported harness. | Doing a single tightly coupled change → the relevant domain skill. |

## Design, experience, visualization and media

| Skill | Short brief and fixture | Functional gate | What better looks like | Near miss and expected route |
| --- | --- | --- | --- | --- |
| `ui-design` | “On my phone I can't tell what needs attention in this inventory.” Provide a working table and a design system or fixed reference. | Data and tasks are preserved, layout reflows and status is readable without color alone. | Review blinded phone, tablet and desktop screenshots for hierarchy, density, typography, alignment and consistency. Check contrast, visible priority items and space spent on redundant boxes or text. | Changing consent order or fixing a confusing recovery path → ux-design. |
| `ux-design` | “People get stuck when payment fails.” Simulate failure and recovery in a checkout. | Values are preserved, an error is associated with the input, focus helps recovery, and retry works. | Observe whether people find the problem and complete the task. Record time, steps, re-entry and ambiguity. Add a reversible task in an unfamiliar language to evaluate navigation and feedback. | `web-motion` | “Make the fossil interactive and usable on a basic phone.” Include a CSS reveal case, a standard viewer and a custom cutaway. | Interaction works, reduced-motion behavior is usable and fallback preserves the content. | Measure when assets load and whether the scene draws at rest. Review short recordings for timing, purpose and clarity, with the same device profile. | Optimizing a static list with no motion → web-performance. |
| `web-performance` | “This list feels slow on a phone.” Give a working app, consistent data volume and a repeatable device and network profile. | Same data and behavior, with critical paths intact. | Compare repeated measurements for load time, bytes, interaction latency and CPU. | `data-visualization-dashboards` | “Show where returns went up.” Include groups with unequal denominators and small samples. | Chart values, periods, units and transformations are correct. | Test whether readers identify the right change and understand its uncertainty. | `media-production` | “Make a short product video.” Supply licensed assets, destination and budget. | The file exports in the requested format and meets rights, captions and basic audio requirements. | Judge the actual render for framing, continuity, sound and fit with the direction. Record production time, file size and cost separately. | Writing a short script with no production requirement → storytelling. |
| `storytelling` | “Turn this account into a short story.” Provide events and details that can be used. | The story preserves required facts, medium and length. | Compare causal flow, tension, voice and payoff blind. Ask a reader to identify the turning point to test whether the story communicates it. | Rendering and exporting an approved video → media-production. |

## Marketing, sales and support

| Skill | Short brief and fixture | Functional gate | What better looks like | Near miss and expected route |
| --- | --- | --- | --- | --- |
| `copywriting` | “Write the top of this landing page.” Supply product facts, audience, proof and one goal. | Claims are supported and there is a single main action. | Blind readers can name the product and next step. Compare clarity, voice, specificity and fit with the audience. | Determining price, terms and offer economics → offers. |
| `offers` | “Make this offer easier to accept.” Supply prices, costs, limits and objections. | Conditions and margin are consistent; there is no invented urgency or guarantee. | Compare clarity, match to objections and sensitivity to changes in assumptions. Measure conversion separately with a real experiment. | Rewriting copy for an already fixed and approved deal → copywriting. |
| `ad-creatives` | “Make a short ad for this product.” Supply visual assets, audience and approved claims. | A script, storyboard or render meets the format and uses supportable claims. | Compare the opening, demonstration, clarity and platform fit in the actual artifact. Treat retention and conversion as separate field measurements. | Diagnosing campaign spend and attribution → paid-traffic. |
| `paid-traffic` | “Acquisition got expensive. Where do I look?” Use synthetic spend, clicks and purchases with noisy attribution. | Calculations are correct and the plan stays within the fixture budget. | Identify the seeded bottleneck, distinguish attribution from causation, and define a test and stop rule. | Writing an ad for a fixed audience and media plan → ad-creatives. |
| `seo-geo` | “Make this page findable.” Provide a local site with duplicates, a search intent and source material. | Crawling behavior in the fixture, canonical URLs and cited facts are consistent. | Inspect HTML, internal links and structured data where relevant. Review intent fit and citation quality. Actual ranking or citation needs separate observation. | Writing interface or landing copy without a discoverability goal → copywriting. |
| `viral-content` | “Make a video people want to share.” Supply topic, audience and format. | The piece is publishable, understandable and factually supported. | Use a rendered prototype and observe comprehension, attention and willingness to share. Distribution and reach are separate measurements. | Building a paid ad for a specific campaign → ad-creatives. |
| `lifecycle-messaging` | “Make a sequence for people who stop halfway through onboarding.” Supply events, eligibility and channels. | Simulated routing respects eligibility, exits and cancellation. | Evaluate transition coverage, duplicate prevention, timing and whether each message gives a clear next step. | Fixing a confusing first-run product interaction → ux-design. |
| `sales` | “This deal stalled. What should I do next?” Use a fictional deal with known objections and open questions. | No invented commitments, discounts or customer facts. | Evaluate evidence-based diagnosis, an executable next step and objection handling in a blinded roleplay. | Handling an existing customer's billing incident → customer-support. |
| `customer-support` | “Reply and decide whether this needs escalation.” Supply a ticket, history and fictional policy. | Reply respects policy and privacy, and escalates when required. | Compare resolution accuracy, clarity, next action and how much avoidable back-and-forth the response creates. | Planning the next step in a prospective deal → sales. |
| `redigir` | Run the guided command on a complete brief and then an incomplete one. | It collects essential inputs, preserves answers and routes the brief correctly. | Count redundant questions and evaluate readiness of the resulting brief. Assess this command flow separately from final copy quality. | Writing final copy from a complete brief without a guided intake → copywriting. |

## Product, research, business and analysis

| Skill | Short brief and fixture | Functional gate | What better looks like | Near miss and expected route |
| --- | --- | --- | --- | --- |
| `market-research` | “Is there a market for this?” Mix views, free signups and paid commitments. | It keeps those signals distinct and does not invent market data. | Evaluate evidence strength, whether the test can disprove the idea, the decision threshold and whether the recommendation reacts to contrary evidence. | Prioritizing a backlog with already established evidence → product-management. |
| `product-creation` | “Turn this validated demand into a product.” Supply a segment, capacity and restrictions. | The initial scope fits the constraints and can be tested. | Assess usefulness and size of the first deliverable, quality of the prototype and fit with a trial involving the target audience. | Testing whether demand exists before building → market-research. |
| `product-management` | “What goes in the next cycle?” Supply a backlog with conflicting signals and dependencies. | Plan respects capacity and dependencies and declares what was cut. | Compare alignment between evidence, goals and priorities, testable acceptance criteria, and response to a capacity change. | Designing a first sellable product from validated demand → product-creation. |
| `business-model-finance` | “Does this operation make money?” Provide synthetic revenue, fees, losses and costs. | Calculations and units match the fixture and distinguish cash from profit. | Evaluate break-even, scenario sensitivity, clear assumptions and whether the recommendation changes appropriately when an input moves. | Investigating a funnel measurement anomaly → growth-analytics. |
| `process-improvement` | “Should we automate approvals?” Include touch time, waiting, exceptions and cost. | Uses the right volumes and costs and distinguishes work from waiting. | Compare diagnosis, rework and capacity estimates, and whether the pilot and payback can be verified. Include a case where automation does not pay. | Choosing a feature for the next product cycle → product-management. |
| `growth-analytics` | “Conversion dropped. Why?” Include a shift in traffic mix and missing events. | Denominators are correct and correlation is not presented as causation. | Evaluate separation of measurement errors from behavior, ability to locate the seeded issue, and usefulness of the next check or experiment. | Reconciling raw totals that are unrelated to funnel behavior → data-analysis. |
| `data-analysis` | “These totals don't match.” Supply duplicates, nulls and a known aggregate. | The output matches expected totals and population. Missing data is explicit. | Evaluate source reconciliation, checks that localize the problem, robustness on a new slice and clarity of assumptions. | Building a repeatable ingestion and backfill pipeline → data-engineering. |

Start with a small number of executable fixtures and reuse their evidence across related cases without reusing one rubric for different goals. Keep deterministic fixture and artifact checks in CI. Run live-model comparisons separately with explicit budgets and maintain the historical Claude aggregate as a separate record.
