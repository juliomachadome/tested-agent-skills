# Railway (and container PaaS in general)

Format: **rule** · why · source `[n]` = number in `BIBLIOGRAPHY.md` · example. Every vendor number was checked 15/11/2026 unless it says otherwise; re-check before a decision that costs money or data.

1. **Deploy with an explicit commit SHA and verify the SHA the service reports.** Redeploy and rollback reuse the source of the selected deployment `[15]`; an API-triggered deploy without a SHA builds whatever the service's source points to (lived failure mode, not stated in the docs). Expose `commit` in `/health` from a build variable and compare it with the SHA you requested.
2. **States** `[15]`: Initializing, Building, Deploying, Active, Completed, Crashed, Failed, Removed. With a healthcheck, Active means the check passed; without one, Active means only that the container started.
3. **Healthcheck** `[14]`: any 2xx passes; default timeout 300 s (variable `RAILWAY_HEALTHCHECK_TIMEOUT_SEC`); the probe comes from host `healthcheck.railway.app`, so a host allow-list must include it (otherwise 400 or "service unavailable"); the probe uses the injected `PORT`. **It is not used after the deployment is live**: add an external monitor.
4. **Draining** `[15]`: the old deployment gets `SIGTERM`, then `SIGKILL` after 0 s by default. Set `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` and handle `SIGTERM`; `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS` keeps the old one running after the new is Active (useful for migrations that need both versions).
5. **Rollback has a retention window** `[15]`: deployments older than the plan's image retention cannot be restored (period not stated on the page). Keep a note of the last known good SHA outside the dashboard.
6. **Never run a delete scoped "to an environment" without reading what it deletes;** to take something offline pause, sleep or scale down. (Lived failure mode; docs carry no warning.)
7. **App sleeping** `[18]`: inactive after 5 minutes without outbound packets (sampled; sleeps in 5-10 min). Pooled DB connections, NTP, framework telemetry, private-network calls and the responses to inbound requests count as outbound. Inbound traffic wakes it, the first request is slow and may get a 502. Applies only to new containers, so redeploy after enabling; sleeping services still hold a slot and are deprioritized; static outbound IPs can keep it awake. Example: a worker that polls every second never sleeps.
8. **Private networking** `[20]`: `SERVICE.railway.internal`, services must be in the same environment, each environment is its own network; put the port in the URL.
9. **Usage limits** `[17]`: minimum hard limit USD 10; reminders at 75% and 90%, notice at 100% when workloads were taken down; hitting the compute hard limit takes **all** workloads offline (the agent hard limit, default USD 5 Hobby / USD 20 Pro, disables only the agent). Raising the limit redeploys stopped services automatically, with a manual fallback. A custom email alert is a soft limit and stops nothing.
10. **Outbound SMTP is disabled on Free, Trial and Hobby;** Pro and above allow it after a redeploy; the docs recommend an HTTPS email API on every plan `[21]`.
11. **Regions** `[19]`: US West, US East, EU West (Amsterdam), Southeast Asia (Singapore). No South America.
12. **Config as Code is deprecated** `[22]`: legacy files keep working until 2026-12-01; the docs point to infrastructure as code. Legacy keys under `deploy`: `healthcheckPath`, `preDeployCommand`, `cronSchedule` (others such as timeout and draining are set by variables or settings). Read the current page before versioning deploy config; this date is within weeks of 15/11/2026.
13. **Pricing** `[16]`: Hobby USD 5/month with USD 5 usage included; Pro USD 20/month with USD 20 included; RAM USD 10/GB-month, CPU USD 20/vCPU-month, egress USD 0.05/GB, volume USD 0.15/GB-month; builds are free. Default per-service ceilings: Hobby 6 replicas, 48 GB RAM, 48 vCPU; Pro 42 replicas. Worked bill in `diagnosis-playbook.md` section 5.
14. **One process doing API + queue + CPU work** blocks requests; the first scale step is a second service with the same code and a role variable (`ROLE=worker`), not replicas. Before adding a replica list per-process state (in-memory limits, caches, locks, schedulers) `[1]`.
15. **Pre-deploy migrations run on every deploy:** idempotent, serialized by a lock, only from the service that owns the schema `[1]`.
