# Vercel

Format: **rule** · why · source `[n]` (see `BIBLIOGRAPHY.md`) · example. Numbers checked 15/11/2026 on the pages cited (page dates: env 2026-09-17, functions limits 2026-08-24, regions 2026-08-11, rollback 2026-07-07, protection 2026-09-15).

1. **A variable change applies only to new deployments; the running one keeps the values it was built with** `[23]`. `NEXT_PUBLIC_*` values are inlined into the client bundle at build, and dynamic lookups such as `process.env[name]` are not inlined. After a change: redeploy, then read the value in the shipped bundle, not in the dashboard.
2. **Environments:** Production, Preview (optionally per branch), Development, plus custom environments `[23]`. In a custom environment `VERCEL_ENV` is `preview`; read `VERCEL_TARGET_ENV` to tell them apart. Preview never gets production keys or the production database.
3. **Variable types are Config (readable by authorized members) and Secret (write-only after saving)** `[23]`. Total size 64 KB per deployment; 5 KB per variable on the edge runtime. Rotate by adding the new value, redeploying, proving, then removing the old one (runbook in `playbooks.md` section 3).
4. **Turborepo caches ignore variables not listed in `env` or `globalEnv`** and may reuse a build made with other values `[23]`.
5. **Deployment Protection** `[27]`: Standard Protection covers all URLs except production domains; "All Deployments" also covers production and is available on every plan; Vercel Authentication needs no add-on; Password Protection is USD 20/month per protected project on Pro (not on Hobby); Trusted IPs and Passport are Enterprise. With Standard Protection the production generated URL (`VERCEL_URL`) is no longer public, so server code must call its own origin.
6. **Automation against protected deployments** `[28]`: header `x-vercel-protection-bypass` (query parameter only if the tool cannot set headers); `x-vercel-set-bypass-cookie: true` for browsers (`samesitenone` for iframes); several secrets per project; deleting or regenerating a secret invalidates earlier deployments, so redeploy; it does not override active DDoS mitigation. Never turn protection off to test.
7. **Instant Rollback** `[26]`: repoints production domains to a previous production deployment; environment variables stay as that deployment was built (no change from settings); **auto-assignment of production domains is switched off afterwards, so new pushes to the production branch do not go live until you promote** (`vercel promote`); Hobby can roll back only to the previous deployment; one rollback or promotion job per project at a time (409 otherwise); cron definitions follow the target deployment. Database changes are not reverted.
8. **Function region** `[25]`: new projects default to `iad1` (Washington, D.C.); set the region next to the database in settings or `vercel.json`; Hobby has one region, Pro up to 5; Enterprise can add failover regions; Routing Middleware runs in all regions anyway.
9. **Function limits with Fluid compute** `[24]`: duration default 300 s everywhere; maximum 300 s Hobby, 800 s Pro and Enterprise (1800 s extended, beta); memory 2 GB / 1 vCPU default, up to 4 GB / 2 vCPU on Pro; request or response body 4.5 MB (streamed responses excluded); bundle 250 MB (500 MB Python; 5 GB beta "large functions"); 1,024 file descriptors shared across concurrent executions, including database sockets. Large files go to object storage by signed URL.
10. **Billing is active CPU time plus provisioned memory time** `[24]`; waiting on I/O is not active CPU, but memory still bills. Set `maxDuration` per route.
11. **Concurrent invocations can share an instance:** module-scope variables are shared between simultaneous requests; keep no per-user data there. File descriptors are shared too, which is why one database pool per instance with `max: 1` matters (`supabase.md`).
12. **Routing Middleware runs on every matching request in every region:** no network calls on the common path `[25]`.
