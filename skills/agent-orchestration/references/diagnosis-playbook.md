# Diagnosis playbook: symptom, likely cause, check, fix

Use it top-down. Step 0 first: if the evidence is a claim, a failed harness or a stale reading, every branch below is noise. Evidence tags: **[C]** official docs or consensus, **[M]** published engineering report or a single serious source, **[F]** practitioner or house rule, **[X]** myth. Numbers marked "est." are planning ranges to replace with a local measurement. Nothing is copied from a source; ideas are applied.

## Step 0: is the evidence trustworthy?
| Check | How | If it fails |
|---|---|---|
| The report is a claim, not a result | open the diff, run `git status` and `git diff --stat`, run the one command that proves it | treat the work as unfinished and label the report "unverified" |
| The harness ran at all | a run that returns empty text, 0 tool calls or 0 tokens is a failed run, not a score of 0 | rerun after the cause is gone; never average it in |
| The window is open | a usage-limit cut-off returns nothing silently and looks like a failing score or a quiet agent **[F]** | check remaining quota first; a batch that returns nothing after the limit is a pause |
| The measuring tool works | a parser that finds zero entries must stop with an error and must not overwrite the previous data **[F]** | keep the old file, print the raw input, fix the parser |
| Same moment | process list, RAM and quota readings taken now, not remembered | re-read `ps`, `vm_stat` or `free`, `/usage` |
| Sample size | one run of an agent or trigger test is an anecdote; use 3+ runs per case and report hits as n/runs **[F]** | say "too few runs to conclude" |
| What changed | model switch, agent file edit, new plugin, new MCP server, longer prompt, a new heavy job | line the change up with the first bad run before naming a cause |

## Symptom to cause to fix
**1. Quota burns fast.** Causes by frequency **[F]**: more live agents than needed; a top-model agent on a routine job; a nested subagent chain; reruns of the same brief; long sessions that re-read a growing context; tool output pasted whole. Check: `/usage` attribution by subagent and skill **[C]**, the ledger of what ran, the model of each agent, the number of turns. Fix: inline for small work, Haiku or Sonnet for routine, one agent per area, the Agent tool removed from workers, outputs capped in the brief, `/clear` between unrelated tasks.

**2. Agent drifts from scope.** Causes: goal stated without limits; "check everything"; the agent found an interesting side issue; a polluted context. Check: compare `git status` paths with the files you declared. Fix: nudge with the original goal quoted, revert out-of-scope files, restart with a lean summary. Prevent: file list, "Do NOT" list, `maxTurns` in the agent definition **[C]**.

**3. Loops and repeated tool calls.** Three to five identical calls in a row, or a read-edit-revert cycle **[F]**. Causes: the check it runs cannot pass (broken test, missing permission), or the instruction contradicts itself. Fix: stop it, read the failing command yourself, send one different approach or do it inline. Do not negotiate for many turns; every turn costs.

**4. Reports success but nothing changed.** Check, in this order: `git status` and `git diff --stat` (empty means nothing changed); `git diff` for skipped tests, loosened assertions, deleted checks, edited fixtures; rerun the proving command yourself and read the count of passed, failed, skipped; compare the files changed with the files promised. Causes: the work happened in another worktree or directory; the agent hit its turn cap and summarised intent; a test was skipped to get green. Fix: reject the report, send the failing output back, escalate to a stronger reviewer if the claim is high-risk **[F]**.

**5. Two agents edit the same file.** Symptoms: lost edits, merge conflicts, a test that passes for one and fails for the other. Fix: assign each file one owner; give parallel writers their own worktree (`isolation: worktree` in the agent definition **[C]**); lockfiles, schemas and indexes get a single owner; helpers that only read write their findings to a file and the owner applies them. Commit with explicit paths, never add-all.

**6. Machine slows or swaps.** Est. RAM per process (measure with `ps -o rss,comm`; the figures differ by project): agent CLI 0.4-0.8 GB; a compile, bundle or test run 1.5-3 GB; headless browser 0.5-1.5 GB; container VM 2-4 GB; a local model run several GB. Budget on 16 GB: OS and everyday apps about 6 GB, container VM 3 GB, leaves about 7 GB. One heavy job (1.5-3 GB) plus 3 agent CLIs (1.2-2.4 GB) = 2.7-5.4 GB, fits. Eight agents each running tests = 8 x (0.4 + 1.5) to 8 x (0.8 + 3.0) = 15-30 GB, well over 7, so the machine swaps. Signals: swap in use and growing, `memory_pressure` warning, fans, agents timing out. Fix: cap at 2-3 live agents, one heavy job, stop containers and servers after each job, close the browser.

**7. A subagent spawns subagents.** By default nesting reaches several layers below the main conversation **[C]**, and cost multiplies silently. Check: the transcript of the subagent for Agent calls. Fix: leave Agent out of the worker's `tools`; write "do NOT spawn subagents" in the brief; set the depth limit in the project settings **[C]**.

**8. Brief too long or too short.** Too short: duplicated work, wrong scope, a question back. Too long: pasted files, rules the agent will skim, no priority. Check: could a competent stranger act on it in one read? Fix: the template in `playbooks.md` section 2; pointers to files, not file contents; the goal and "done when" first.

**9. Results contradict.** Causes: different data cut, different date, one agent guessed, different definitions. Check: ask each for the source of the number and the command that produced it; rerun both on the same input. Fix: one verifier with both outputs and the raw source; mark unresolved items as unknown instead of picking one.

**10. Background task never notifies.** Causes: a permission prompt is waiting; the process died; the wait polls a process that is not yours; the session closed. Check: the task list or process list, the output file, whether the approval surfaced in the main session **[C]**. Fix: bounded waits, not endless loops; relaunch with the needed tools pre-approved; do not poll in a tight loop.

**11. Permission denied reading files.** A headless `claude -p` run cannot read outside its working directory unless the folder is added with `--add-dir`, and a tool must be allowed with `--allowedTools` or no prompt can be answered **[C]**. In a subagent, the tool list and permission mode decide. Check the exact error text. Fix: add the directory, allow only the tools needed, keep the run in an empty temporary directory so a mistake touches nothing.

**12. Wrong model for the task.** Signs: Haiku invents or skips steps on judgement work; the top model rewrites a rename; the effort is inherited by accident. Check: the agent definition and the resolved model **[C]**. Fix: the table in `playbooks.md` section 3; set `model` and `effort` in the definition. A model alias moves with releases, so date any hard-coded choice.

**13. Routing picks the generic agent over the specialist.** Causes: the specialist's description is vague, overlaps with a neighbour, or lacks the user's words; the task text names no domain. Check with a routing test (`playbooks.md` section 7): several runs per task, all agents loaded. Fix: put the trigger phrases and the "does not do X (that is agent Y)" tail in the description; keep descriptions distinct; re-test.

**14. An eval score of 0 that the harness caused.** Common causes **[F]**: agent files symlinked inside a plugin are not loaded (copy them); a routed subagent runs the whole task unless the test stops at the tool call; the run cannot read the skill files without the directory added and the tools allowed; the judge's reply is not clean JSON (parse the first JSON object, never the whole text); the quota ran out mid-batch. Check: the raw output of one run by hand, the count of empty results, whether the skill or agent was loaded at all. Fix the harness, rerun, and only then read the score.

## Worked numbers (illustrative; replace with measured values)
- **Token cost per agent.** List prices checked 2026-11-15 **[C]**: Sonnet 5.5 $2 in, $10 out, cache write $2.50, cache read $0.10 per million tokens; Haiku 5.5 $0.10 / $0.50 / $0.125 / $0.01; Opus 5.5 $8 in and $40 out (cache columns assumed 4x Sonnet, not read). A working agent: 25 turns, 45k tokens of context re-read from cache each turn, 15k fresh input, 12k output. Sonnet: cache reads 25 x 45k = 1.125M x $0.10 = $0.11; cache write $0.11; fresh input $0.03; output $0.12; total about $0.38. The same job is about $0.02 on Haiku and about $1.50 on Opus. A light lookup (8 turns, 15k context, 3k out) is about $0.09 on Sonnet. Subscription plans meter usage differently; use these as relative weights and read the real figure in `/usage`. Anthropic measured about 15x the tokens of a chat for multi-agent runs and about 4x for a single agent **[M]**.
- **Coordination cost.** Pairwise paths between n workers = n(n-1)/2: 3 workers 3, 4 workers 6, 8 workers 28 **[C]** (the idea is from Brooks). Each path is a place where scope, files or findings can clash, and you verify every report.
- **Parallel versus sequential.** Four tasks, each 3 min to write and 3 min of heavy test run, 2 min for you to verify. Sequential: 4 x 8 = 32 min. Parallel writers with one heavy slot: writing overlaps (3), the four heavy runs queue (12), verification queues (8) = 23 min. The gain is 9 min, not 4x, because the bottleneck is the single heavy job and your verification. By Little's law (work in progress = throughput x time) **[C]**, more agents above the bottleneck raise the queue, not the output.
