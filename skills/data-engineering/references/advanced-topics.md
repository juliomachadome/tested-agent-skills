# Advanced topics: streaming, semantic layer, reverse ETL, CI, catalog, ML features

Tags as elsewhere. Open this only after the batch basics (`ingestion.md`, `modelling.md`, `quality.md`) hold.

## 1. Streaming and stream processing
**When batch is enough [F].** If the decision is made daily or hourly, run micro-batches (every 5-15 minutes) from the same SQL; streaming adds state, ordering, on-call load and cost. Choose streaming when a person or system must react in seconds: fraud checks, alerts, live inventory, operational dashboards.
**Pieces.** A log or broker (Kafka, Kinesis, Pub/Sub are examples) holds ordered events per partition; a processor (Flink, Spark Structured Streaming, Beam, or SQL in the warehouse) reads, aggregates and writes a sink. Partition by the key whose order matters (customer id); order is only guaranteed within a partition **[F]**.
**Delivery.** Assume at-least-once and make the sink idempotent: upsert on a unique key, or write by (partition, offset) so a replay overwrites itself **[C]** (Kleppmann). Broker-level "exactly-once" settings cover reads and writes inside the broker's own system; a write to an external database is still only as safe as the sink's idempotence **[F]**, so keep the dedupe key. Not verified against the Kafka documentation this pass.
**Time.** Event time (timestamp in the record) gives results that follow the data; processing time follows the clock and varies with arrival speed. A watermark says "events up to time T should have arrived", letting windows close; allowed lateness accepts events after that at the cost of delaying or revising results **[C]** (Flink docs, Akidau et al.). Window types: tumbling (fixed, no overlap), sliding, session (gap of inactivity). Choose watermark delay from the measured lateness distribution; late beyond that go to a correction batch.
**Pattern for small teams [F].** Stream into raw tables, run the same dbt models on a short schedule, and keep one corrections job per day that rebuilds the recent partitions. Add a true stream processor only when sub-minute latency is a written requirement.

## 2. Semantic layer and metric definitions
Problem: each dashboard re-derives "revenue" with different filters. Fix: define each metric once, in version-controlled code, with entities (join keys), dimensions and a metric type (simple, ratio, cumulative, derived, conversion), and let tools query that definition **[C]** (dbt docs on MetricFlow). dbt's semantic layer and Cube are examples; a plain mart model that BI tools read is also a valid "one place" for small teams. Rules: one owner and one name per metric; a description with the filters (paid only? net of refunds? timezone?); a test that the metric equals the source total on a known day; a change log when a definition changes, since history will move. Ratios are defined from numerator and denominator, not averaged **[C]**.

## 3. Reverse ETL (warehouse to CRM, ads, support tools)
Syncs modelled tables back to operational tools (managed tools or a small script). Design **[F]**: a model with one row per target record and a stable external id; sync by upsert on that id; send only changes; log sent, failed, skipped; rate limits and retries with backoff; a dry-run mode; a kill switch. Risks: sending wrong data to customers or ad platforms is harder to undo than a bad dashboard, so gate with tests on the source model and sample review before the first sync. Personal data leaving the warehouse needs a lawful basis, consent status as a column that the sync honours, minimisation (send hashed or only needed fields where the destination supports it) and a deletion path; the law goes to the privacy law of the data subject's country (official regulator pages) and campaign use to paid-traffic and growth-analytics.

## 4. dbt CI and environments
Three environments **[F]**: dev (personal schema per developer, small data sample or limited date range), staging or CI (schema per pull request, built from the PR, dropped after), prod (built by the scheduler, only from the main branch). Credentials differ per environment; developers cannot write to prod.
**Slim CI.** Keep the production `manifest.json` as state. On each PR build only what changed and what depends on it: `dbt build --select state:modified+ --defer --state <prod-manifest-dir>`; unchanged parents are read from prod through deferral **[C]** (dbt docs). Caveats from the docs: `state:modified` compares code and config, not data; tags and meta changes do not count; do not point `--state` and the target path at the same folder; on a schedule with no code change it can build nothing, so use it for CI and merge jobs; relationships tests across environments can mismatch so consider excluding them in CI **[C]**.
**PR checks [F].** Compile and parse, build changed models, run their tests, fail on new warnings above a threshold, a row-count or total diff against prod for changed marts, lint SQL, require a description and tests for new models, a contract on models other teams use. Deploy by merge, never by hand-run.

## 5. Catalog and lineage tools
Start with what dbt gives: the docs site with descriptions, owners (in YAML meta) and the lineage graph **[C]**. Add a catalog (open source or commercial; examples include DataHub and OpenMetadata, not opened this pass) when several tools and teams need search, ownership, glossary and cross-tool lineage **[F]**. The OpenLineage specification records jobs, runs and datasets with facets so tools can share lineage **[C]**. A catalog with no owner assigned to each table decays; budget the upkeep.

## 6. ML feature pipelines
Same idempotent pipelines, plus two hazards. **Point-in-time correctness**: when building training rows, join each row to the feature values as they were known at that row's timestamp, never the latest values; otherwise future information leaks into training and offline metrics look better than production **[C]** (Feast docs). Late corrections and backfills also leak unless a created-at (availability) timestamp is used in the join. **Training-serving skew**: compute training features and online features from one definition and one code path, or test that they match on a sample **[F]**. Keep feature definitions versioned, with owner and freshness checks. Model training, evaluation, prompts, retrieval and LLM features go to llm-engineering; experiments to growth-analytics.
